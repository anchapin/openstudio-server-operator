==== ISSUE #721 ====
`status_store._conflict_backoff` (`status_store.py:183`) computes the backoff as `_BACKOFF_BASE_SECONDS * (2 ** (attempt - 1)) * (0.5 + random.random())` — the jitter is multiplicative only, with NO upper bound. After `MAX_CONFLICT_RETRIES = 5` attempts, the worst-case cumulative sleep is `1.0 * (1 + 2 + 4 + 8) * 1.5 = 22.5 s` of pure sleep BEFORE the conflict is escalated to `StatusStoreConflictError`.

The SLA poll cadence is 30 s (`SLA_POLL_INTERVAL_SECONDS`); a sustained 409 storm on a status PATCH during a tick can spend 22.5 s sleeping inside the wrapper's RMW cycle, leaving only 7.5 s for the actual REST/Redis work — or worse, the cumulative sleep plus the actual work exhausts the cadence budget so the next kopf tick cannot start on time (kopf's timer cadence is wall-clock-aligned; a tick that overruns is silently skipped, no count).

The `BoundedK8sRequest` (#579) explicitly cites this concern as motivation but only for the network surface; the status-store retry loop has the same concern on the `.status` subresource path.

Acceptance criterion: bound the conflict-sleep ceiling to `min(_conflict_backoff(attempt), MAX_CONFLICT_SLEEP_SECONDS)` where the ceiling is well inside the shortest timer cadence (e.g. 2.0 s, making worst-case cumulative 9 s). Add a regression test that monkey-patches `_sleep` to capture the sleeps, forces a 5-409 storm, and asserts `sum(sleeps) < SLA_POLL_INTERVAL_SECONDS * 0.5`.

Scope guard: Do NOT change the retry COUNT (`MAX_CONFLICT_RETRIES`); only the per-attempt sleep ceiling is in scope.

## Why this is now actionable

  copy the schema.

The wiring is mechanical — the design *decision* is which handler gets the call site.

## Two viable call sites (decision in sub-issue #709)

1. **SLA escalation fallback** (`handlers/analysis_sla.py`, between soft-stop and pod
   eviction). After `gracefulStopTimeoutMinutes` of still-`started`, try one
   `stop_analysis` POST and wait for it; only escalate to pod eviction if the
   in-flight runs do not finish in a bounded budget. *Effect: fewer wedged-pod
   evictions on analyses that just need a few more seconds to finish naturally.*

2. **Retention pre-delete gate** (`retention.py`, before `delete_analysis`). When the
   prune CronJob sees a `started` analysis at verification tick time, issue
   `stop_analysis` first, wait for the analysis to reach `completed`/`na`, then
   `delete_analysis`. *Effect: zero in-flight runs killed by NFS cascade; storage
   semantics become "graceful" rather than "forceful".*

Both paths use the same wiring shape (D11 gate + D04 anchor + marked Event). The
choice is purely a UX question (which operator-level guarantee to prioritize) and
*must be made before any code lands* — the config field name, anchor key shape, and
metric labels all branch on it.
