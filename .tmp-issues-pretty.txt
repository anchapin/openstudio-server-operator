==== ISSUE #717 — Add SIGTERM graceful-shutdown handler so mid-tick writes are ====
  The operator runs as a Kubernetes Deployment (single-replica, Recreate strategy, AGENTS.md). kopf's own teardown is event-driven; the operator has no `signal.SIGTERM` / `atexit` handler in `handlers/__init__.py` or `prune_entrypoint.py`. Three consequences matter against the project goals:

(1) A SIGTERM mid-tick (kubelet rolling the pod or a node-drain Evict) drops the current timer body — accepted by the D12 idempotency design (the persisted `.status` anchors are the source of truth and a fresh process re-reads them).

(2) BUT the in-memory `QueuedKopfEventSink._queue` (`events_sinks.py`) holds entries that were ACCEPTED into the persisted mirror just before SIGTERM; while the persisted mirror is the at-least-once contract and a fresh process emits them exactly once via persisted-first drain, the queue is lost between drain and SIGTERM — fine for current semantics, BUT the marker writes that depend on a successful RMW (`mark_soft_stop_escalated`, the #649 ineffective-restart counter, the #402 deferred-event append) can lose their final byte if SIGTERM lands mid-write.

(3) The `WorkerPodApi.delete_namespaced_pod` loop (`analysis_sla.py:566-585`) is per-pod try/except (issue #118 noted); a SIGTERM during the loop loses the partial-eviction accounting AND the `mark_soft_stop_escalated` write that follows. The D12 accepted race ("re-attempt on next tick") holds for a clean crash, but a SIGTERM during a tick that already wrote the eviction(s) but not the marker leaves the eviction REAL and the marker ABSENT — the next tick re-fires the same evict list.

Install a `signal.SIGTERM` handler that (a) prevents new tick invocations (kopf's shutdown event), (b) waits for the in-flight tick to complete with a bounded grace (`terminationGracePeriodSeconds` minus 5 s), (c) flushes any pending status-store writes from the in-flight tick body.

Acceptance criterion: Add a regression test that injects SIGTERM between the pod-delete loop and `mark_soft_stop_escalated` and asserts the marker is written before exit (or that the next-tick re-fire is correctly recorded as the SAME restart, not a second restart).

Scope guard: Do NOT add `@kopf.on.delete` or `@kopf.daemon` handlers (the #681 persistence-fence rule); this issue only installs SIGTERM handling at the process level.

==== ISSUE #709 — Decide call site for stop_analysis: SLA escalation fallback  ====
  Tracking the design decision that unblocks #710 (D11 gate wiring) and #711
(regression tests) per #707 (epic).

## Context

`stop_analysis` (POST `/analyses/{id}/action` with `analysis_action=stop`) is a
**waiting-variant** stop — it sets `run_flag` false and waits for in-flight runs
to complete. This is semantically distinct from the existing two stops:

| Method | Wait? | Used by today |
|--------|-------|---------------|
| `soft_stop_analysis` (GET `/analyses/{id}/soft_stop`) | No (returns immediately, in-flight runs continue) | `handlers/analysis_sla.py:381` — primary SLA action |
| `stop_analysis` (POST `/analyses/{id}/action`) | **Yes** (sets `run_flag` false + waits) | **no call sites** |
| `delete_analysis` (DELETE `/analyses/{id}`) | n/a (cascade) | `retention.py` — NFS cleanup |

## Two candidates

### Candidate A — SLA escalation fallback (handlers/analysis_sla.py)

After the SLA handler's `gracefulStopTimeoutMinutes` grace period expires and the
analysis is STILL `started`, try ONE `stop_analysis` POST before escalating to
pod eviction. Bounded budget (e.g., `stopWaitTimeoutSeconds = 60`) for the wait;
on timeout, fall through to the existing pod-eviction path.

**Pros**
- Reduces wedged-pod evictions: analyses that just need a few more seconds to
  finish naturally get to finish.
- No new CRD field needed — the trigger is the existing SLA grace expiry.
- Pure UX improvement; same control surface.

**Cons**
- Adds wall-clock time to the SLA tick (must wait up to the budget per analysis).
  Acceptable since soft_stop has already failed to act fast enough.
- Cross-cuts the SLA handler — bigger test surface than a brand-new handler.

### Candidate B — Retention pre-delete gate (retention.py)

When the prune CronJob's verification tick sees a `started` analysis scheduled
for delete, issue `stop_analysis` first; wait until the analysis reaches
`completed` / `na`; then issue `delete_analysis`. Bounded by a configurable
`preDeleteDrainTimeoutMinutes` (default 30); on timeout, log a Warning Event
and proceed with the delete anyway (preserves current operational guarantee).

**Pros**
- Zero in-flight runs killed by NFS cascade — semantically "graceful".
- Matches user mental model: "delete" implies "let me drain first".
- Isolated to retention — test surface is small (one new tick phase).

**Cons**
- Adds up to `preDeleteDrainTimeoutMinutes` wall-clock per `started` analysis
  in the prune window. If many `started` analyses are scheduled for delete, the
  prune tick's wall time grows linearly.
- New CRD `spec.retention.preDeleteDrainTimeoutMinutes` field becomes a
  precedent for per-tenant retention knobs (gate against spec-bloat).

## Decision criteria

| Question | Candidate A | Candidate B |
|----------|-------------|-------------|
| Which operator-level guarantee is the SLA / retention contract currently failing to provide? | Pod-eviction false positives (analyses evicted that would have finished naturally) | NFS cascade kills in-flight runs |
| Is the underlying wait bounded? | Yes (`stopWaitTimeoutSeconds`) | Yes (`preDeleteDrainTimeoutMinutes`) |
| Is the failure mode understood? | Yes — fall through to existing pod-eviction path | Yes — proceed with delete after timeout |
| Does it add a new CRD field? | No | Yes (`spec.retention.preDeleteDrainTimeoutMinutes`) |
| Test surface delta | Medium (extends SLA handler tests) | Small (new retention tick phase tests) |

## Acceptance criterion

This issue closes when:
1. One of the two candidates is selected.
2. The rationale (1-2 paragraphs) is recorded in this issue body under
   "Decision".
3. The choice is cross-linked into #707's epic body in the "Call site" section.
